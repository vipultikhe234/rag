The source of truth is my existing application database. The system manages:

1. Products
2. Brands
3. Categories and subcategories
4. Product attributes and attribute values
5. Product variants

The semantic search system must use the relationships between these entities to retrieve relevant products without creating unnecessary duplicate embeddings.

Do not immediately start coding. First inspect the existing project, research relevant official documentation, understand the database relationships, and propose an implementation plan.

## 3. Embedding strategy

Implement the following entity-specific strategy.

### A. Product embeddings — required

Products are the primary semantic search targets.

Generate an embedding from a normalized product search document containing relevant information such as:

- Product name
- Product description
- Category and subcategory names
- Brand name
- Relevant product specifications
- Important product features
- A concise summary of variant options when useful

Example source data:

Product:
- Name: Samsung Galaxy S Series
- Description: Smartphone with an advanced camera and display.
- Category: Mobile Phones
- Brand: Samsung
- RAM: 12 GB
- Variants:
  - 256 GB storage, Black
  - 256 GB storage, Blue
  - 512 GB storage, Black

Example normalized search text:

"Samsung Galaxy S Series smartphone. Category: Mobile Phones. Brand: Samsung. Specifications: RAM 12 GB. Available options include 256 GB storage in Black and Blue, and 512 GB storage in Black."

Generate one primary embedding per product, unless the existing requirements justify multiple embeddings for different product sections.

Do not generate a new embedding on every user search. Store and reuse product embeddings until their source content changes.

### B. Brand embeddings — optional and requirement-driven

Support separate brand embeddings only when semantic brand discovery is required.

Example query:
"Which brands make reliable gaming laptops?"

A brand search document may contain:

- Brand name
- Brand description
- Product categories served, if available
- Relevant brand metadata

Do not automatically create brand embeddings just because a brand record exists.

If the application only needs to find products belonging to a particular brand, use product embeddings with structured brand IDs or exact brand filters.

### C. Category embeddings — optional and requirement-driven

Support separate category embeddings when users need semantic category discovery.

A category search document may contain:

- Category name
- Category description
- Parent category
- Relevant child category names

Do not create category embeddings solely to filter products by category. Use category IDs and structured filters for exact category matching.

When a category or parent category changes, update affected product search documents where the category information appears in their searchable text.

### D. Attribute embeddings — generally not required

Store attribute definitions and values in the source database.

Examples:
- RAM: 12 GB
- Storage: 512 GB
- Color: Black
- Material: Cotton
- Screen size: 15.6 inches

Include relevant attribute names and values in product search text.

Do not create an embedding for every attribute definition or attribute value by default.

If future requirements include semantic attribute discovery, implement it as a separate capability rather than mixing attribute embeddings into the product vector collection without a clear use case.

### E. Variant embeddings — generally not required initially

Variants represent purchasable combinations of product options.

Examples:
- Samsung phone, 256 GB, Black
- Samsung phone, 512 GB, Blue
- T-shirt, Large, Cotton, Blue

Store variant information in structured records.

Include a concise variant summary in the parent product's search document when useful. Do not include every variant if doing so creates excessively large documents or reduces search relevance.

Do not create one vector per variant by default.

For exact SKU search, option matching, current price, and stock availability, query the authoritative product variant and inventory records.

If later requirements demand independent semantic retrieval of variants, design a separate variant-indexing strategy with a clear justification.

## 4. Vector storage design

Inspect the existing database and select the appropriate vector storage mechanism.

If PostgreSQL and pgvector are already used or selected, evaluate a dedicated table such as `product_embeddings`.

If MongoDB Atlas Vector Search is used, evaluate the existing collection and vector index design.

The stored embedding record should contain the fields appropriate to the selected database, including:

- Embedding record ID
- Entity type
- Source entity ID
- Normalized searchable text or its version/hash
- Embedding vector
- Embedding model identifier
- Embedding dimensions
- Source content version or hash
- Indexing status
- Last successful indexing timestamp
- Error details where appropriate

For a product-first implementation, use a dedicated product embedding collection or table. Add separate brand or category embedding storage only if those semantic discovery features are approved.

Maintain unique constraints or equivalent safeguards to prevent duplicate current embedding records for the same product and embedding configuration.

Do not store sensitive user information in embedding documents.

## 5. Embedding provider

Inspect the current project's provider and configuration before implementation.

If no provider exists, propose an appropriate provider and document the trade-offs between hosted APIs and local embedding models.

Requirements:

- Keep API keys in environment variables or the existing secrets mechanism.
- Never hardcode API keys.
- Configure the embedding model through application configuration.
- Use the same compatible model and vector dimensions for indexing and query embeddings.
- Validate the vector dimension before saving or querying.
- Handle provider timeouts, rate limits, and temporary failures.
- Add bounded retries and appropriate error handling.
- Avoid silently changing embedding models.
- If the embedding model changes, support a controlled re-embedding and index migration process.

Do not regenerate all embeddings on every application startup.

## 6. Product indexing and synchronization

Create a centralized product indexing service.

Its responsibilities should include:

1. Load the product and relevant related records.
2. Verify that the product is eligible for indexing.
3. Construct a deterministic normalized search document.
4. Compute a content hash or version.
5. Skip embedding generation if the searchable content has not changed.
6. Generate the embedding when required.
7. Upsert the embedding using a stable product identifier.
8. Record indexing status and errors.
9. Prevent duplicate processing from creating duplicate records.

Implement synchronization for these events:

### Product created

Create or schedule a product indexing job after the product has been saved successfully.

### Product updated

Regenerate the embedding only when searchable product content changes, such as name, description, category, brand, or relevant specifications.

### Brand updated

When a brand name or description changes, identify affected products.

Rebuild their search documents and regenerate their embeddings only when the normalized product text changes.

### Category updated

When a category name or description used by product search changes, identify affected products and refresh their search documents.

Handle parent category changes and category hierarchy updates correctly.

### Attribute value updated

When a product's searchable attribute values change, refresh that product's search document.

Do not regenerate embeddings for unrelated products.

### Variant created, updated, or deactivated

Rebuild the parent product's variant summary when appropriate.

Do not regenerate the product embedding for a stock-only or price-only update unless those values are intentionally part of the searchable semantic text.

Maintain current prices and inventory in structured storage rather than relying on potentially stale embedded text.

### Product deactivated

Prevent the product from appearing in normal user search results.

Use an indexed status filter, source-database eligibility check, or equivalent reliable mechanism.

Preserve historical data and embedding records according to the project's retention policy.

### Product reactivated

Make the product eligible for indexing and normal search again. Verify that its embedding is current.

## 7. Reliable asynchronous processing

If embedding generation uses an external provider or a local model that may take significant time, do not unnecessarily block admin CRUD requests.

Evaluate a background job or transactional outbox approach.

Where transactional outbox is appropriate:

1. Save the product changes and an indexing event in the same database transaction.
2. A worker reads pending indexing events.
3. The worker loads the latest product data.
4. It builds the normalized search document.
5. It generates the embedding.
6. It upserts the vector record.
7. It marks the event as completed.

Implement retry handling for transient failures, bounded exponential backoff where appropriate, idempotency, error logging, and a mechanism to inspect failed jobs.

Prevent old jobs from overwriting newer product embeddings. Use a version or content-hash check before applying results.

Do not implement a separate queue or outbox if the existing infrastructure already provides the required reliability. Explain the selected design in the architecture documentation.

## 8. Semantic search API

Implement a semantic product search API consistent with the existing application.

Example conceptual endpoint:

`GET /api/products/semantic-search?q=<query>`

Adapt the actual route and response to the project's API conventions.

Search flow:

1. Validate the query.
2. Generate an embedding for the query.
3. Perform vector similarity search.
4. Retrieve candidate product IDs and similarity scores.
5. Apply active product, category, brand, and other supported filters.
6. Retrieve authoritative product and variant details.
7. Validate current status, price, and stock where required.
8. Return ranked products with relevant information and pagination where supported.

Example query:

"Find a Samsung phone with 512 GB storage."

The system should identify semantically relevant products and use structured filters or variant-level checks to verify the requested brand and storage configuration.

Do not rely on embedding similarity alone for exact constraints such as:

- Brand ID
- Category ID
- SKU
- Price range
- Exact storage capacity
- Available stock
- Product status

Where appropriate, use hybrid retrieval combining vector similarity and structured or lexical search.

Do not use an LLM simply to perform vector similarity search. An LLM is optional for query interpretation, reranking, or generating a natural-language response when there is a clear benefit.
